# Lib.Db v2.2.1 Blocker Fix Report

이 문서는 v2.2.1에서 실 DB 검증 중 확인된 차단 이슈와 수정 내용을 정리합니다.

## 요약

| 영역 | 문제 | v2.2.1 처리 |
|---|---|---|
| 기본 ResultSet 매핑 | SQL 컬럼 `CELL_NO`가 positional record `CellNo`와 매핑되지 않아 `0` 기본값으로 채워짐 | exact match 후 `_` 제거 + 대소문자 무시 fallback 적용 |
| `[DbResult]` generated mapper | Diagnostic monitor가 반환하는 `MonitoredSqlDataReader : DbDataReader`를 `SqlDataReader`로 cast해 `InvalidCastException` 발생 | Source Generator와 runtime mapper를 `DbDataReader` 우선 경로로 전환 |
| `DateOnly`/`TimeOnly` 파라미터 | Raw SQL `DateOnly`가 JSON/string 또는 부정확한 SQL 타입으로 전송되어 SQL 변환 오류 가능 | Raw SQL 및 SP 바인딩 모두 `DateOnly -> date`, `TimeOnly -> time` 명시 보정 |
| SQL Server DDL | computed column index 계열에서 `SET QUOTED_IDENTIFIER ON` 필요 | 검증 DDL에 명시하고 index 생성 여부를 테스트 |

## 1. ResultSet 이름 convention

### 원인

기존 `ExpressionTreeMapper<T>`는 컬럼명과 프로퍼티명을 `StringComparer.OrdinalIgnoreCase`로만 비교했습니다.

```sql
SELECT CELL_NO, SLOT_NAME
```

```csharp
public sealed record SuspendRow(int CellNo, string SlotName);
```

이 조합에서는 `CELL_NO`와 `CellNo`가 다른 이름으로 판단되어 constructor argument가 `default(int)`로 채워졌습니다.

### 수정

기본 DTO 매퍼에 보수적 SQL identifier resolver를 추가했습니다.

1. exact/case-insensitive match 우선
2. `_` 제거 + 대소문자 무시 fallback
3. normalized collision은 fallback에서 제외
4. 같은 property가 여러 컬럼에 중복 매칭되면 첫 번째 컬럼만 사용

이 규칙은 ResultSet 매핑, SP input parameter 매핑, output parameter 역매핑에 적용됩니다.

## 2. `[DbResult]` + monitored reader

### 원인

v2.1/v2.2 기존 generated mapper는 `Map(SqlDataReader)`를 생성했고, runtime `GeneratedResultMapper<T>`도 `DbDataReader`를 `SqlDataReader`로 cast했습니다.
하지만 resilient streaming path는 연결 수명과 메트릭을 reader dispose에 묶기 위해 `MonitoredSqlDataReader : DbDataReader` wrapper를 반환합니다.

### 수정

Source Generator는 다음 overload를 생성합니다.

```csharp
public static T Map(DbDataReader reader);
public static T Map(SqlDataReader reader) => Map((DbDataReader)reader);
```

runtime mapper는 `Map(DbDataReader)`를 우선 찾고, 없을 때만 legacy `Map(SqlDataReader)`를 사용합니다.
legacy mapper만 있는 상태에서 wrapper reader가 들어오면 재생성이 필요하다는 명확한 예외를 반환합니다.

## 3. `DateOnly`/`TimeOnly` 파라미터

### 원인

Raw SQL 바인딩에서 `DateOnly`와 `TimeOnly`가 primitive scalar로 분류되지 않아 JSON/string 경로 또는 `Variant` fallback으로 흐를 수 있었습니다.
SP 메타데이터 기반 바인딩도 SQL Server `date`/`time`이 기대하는 CLR 값으로 명시 보정하지 않았습니다.

### 수정

| CLR 타입 | SQL Server 타입 | 전송 값 |
|---|---|---|
| `DateOnly` | `SqlDbType.Date` | `DateTime` 00:00:00 |
| `TimeOnly` | `SqlDbType.Time` | `TimeSpan` |

Raw SQL과 저장 프로시저 바인딩 양쪽에서 동일한 보정이 적용됩니다.

## 7. Codex Security 리뷰 결과

변경 diff 기준 보안 리뷰 결과:

- P0/P1 security blocker 없음
- 새 SQL DDL/DML은 테스트 DB fixture의 안전 검증 이후 실행됩니다.
- 새 검증 SQL은 고정 리터럴 기반이며 사용자 입력을 동적 SQL로 연결하지 않습니다.
- 연결 문자열, 토큰, 비밀번호는 코드와 문서에 추가하지 않았습니다.
- `DenyWriteText`는 guardrail이며 SQL parser 또는 독립 보안 경계로 과장하지 않습니다.

## 8. 남은 책임 경계

- 오래된 generator 산출물을 포함한 외부 바이너리는 `Map(DbDataReader)` overload가 없을 수 있습니다. 새 `Lib.Db.TvpGen`으로 재빌드해야 합니다.
- ResultSet convention fallback은 `_` 제거 + 대소문자 무시까지만 지원합니다. 다른 naming convention은 명시 매핑 또는 DTO 이름 조정이 필요합니다.
- 검증 DB DDL은 테스트 DB 전용입니다. 프로덕션 DB에는 운영 migration/release 절차로 배포해야 합니다.
