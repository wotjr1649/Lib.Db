# Lib.Db v2.6.3 Brainstorming Backlog

Status: Deferred brainstorming backlog after v2.6.2 design gate
Last reviewed: 2026-07-05

## Scope Boundary

The items below are intentionally out of scope for v2.6.2. They require broader API, compatibility, tooling, or dependency decisions than a focused hardening patch should carry. Revisit them only after v2.6.2 security, cache, configuration, documentation, and release-verification work has shipped or been explicitly abandoned.

## Deferred Topics

### Full SQL Parser

- Brainstorm whether Lib.Db should ever parse full SQL text, or whether `RawSqlPolicy` should remain a conservative guardrail only.
- Evaluate false-positive and false-negative risk, SQL Server dialect coverage, comment/string/bracket handling, dynamic SQL, stored procedure calls without `EXEC`, and maintenance cost.
- Do not treat a parser as a replacement for least-privilege database accounts, stored procedure boundaries, or `RawSqlPolicy.DenyAllText`.

### DB Introspection And Scaffold

- Brainstorm metadata inspection and scaffold workflows for SQL Server objects.
- Keep production DDL/DML execution explicit, reviewable, and opt-in.
- Avoid cloud-database assumptions unless a future requirement explicitly changes the local/direct SQL Server boundary.

### Generator Package

- Brainstorm a separate generator package rather than adding generator behavior to the core runtime package.
- Prefer checked-in schema inputs and additional files over live database access during normal compilation.
- Package generator assets as analyzer assets instead of runtime dependencies.

### Public API Large Redesign

- Brainstorm breaking or large public API changes only in a future compatibility window.
- Include migration guides, deprecation path, binary/source compatibility checks, and consumer impact review.
- Do not fold this into v2.6.2 hardening work.

### Legacy Bulk Default Breaking Change

- Brainstorm whether legacy reflection `BulkInsertOptions` defaults should align with AOT-safe `BulkWriteOptions`.
- Treat changes such as making constraint checks stricter by default as breaking unless compatibility evidence proves otherwise.
- Prefer documentation and opt-in behavior before a future breaking release.

### Broad Dependency Churn

- Brainstorm dependency policy separately from v2.6.2 patch-level servicing updates.
- Require restore/build/test/AOT/package verification and vulnerability/deprecation checks for any broad dependency update.
- Avoid changing multiple dependency families in a hardening patch unless the update directly resolves a validated issue.

### Bulk Progress Notification API Shape

- Brainstorm whether Lib.Db should expose `SqlBulkCopy.NotifyAfter` and `SqlRowsCopied` through a callback, `IProgress<long>`, diagnostics event, or no public API.
- Resolve staged-operation semantics before implementation because update/delete/upsert paths use stage loading plus ordinary target DML.
- Do not add this to v2.6.2 unless a later design gate narrows the API and proves compatibility.

### Narrow Bulk Copy Destination Options

- Revisit `TableLock` and `KeepNulls` as additive SQL Server bulk-copy knobs after v2.6.2 hardening ships.
- Define whether these options affect only direct `BulkInsertAsync` destination copy, staged table loading, or both; document misleading staged-operation cases explicitly.
- Require compatibility, docs, unit tests, verification DB tests, and AOT-safe bulk shape coverage before promotion.

## Exit Criteria For Promoting Any Item

- Written problem statement and concrete user value.
- Compatibility analysis and migration story.
- Security and data-exposure review.
- TDD-ready task breakdown.
- Verification matrix covering unit, integration, AOT/trimming, packaging, and docs where applicable.
