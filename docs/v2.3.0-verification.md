# Lib.Db v2.3.0 Verification Runbook

Updated: 2026-05-19

This runbook defines the release-grade verification flow for the v2.3.0 runtime TVP work. It keeps DB setup, matrix tests, coverage gates, BenchmarkDotNet reports, and artifact scanning in one repeatable path.

- BenchmarkDotNet exporters: default reports are written below `BenchmarkDotNet.Artifacts/results`, with CSV, HTML, and Markdown exporters available: <https://benchmarkdotnet.org/articles/configs/exporters.html>

- Microsoft Learn: memory-optimized table variables can be passed as TVPs and SQL Server requires a `MEMORY_OPTIMIZED_DATA` filegroup for memory-optimized features: <https://learn.microsoft.com/en-us/sql/relational-databases/in-memory-oltp/faster-temp-table-and-table-variable-by-using-memory-optimization>

## Environment Contract

Connection string values are never printed by the automation. The scripts only print whether the expected keys are present.

Required for full DB matrix tests when complete connection strings are supplied through environment variables:

- `LIBDB_TEST_CONNECTION_VERIFICATION`
- `LIBDB_TEST_CONNECTION_SORTER`
- `LIBDB_TEST_CONNECTION_STRESS`
- `LIBDB_TEST_CONNECTION_CHAOS`
- `LIBDB_TEST_CONNECTION_BENCHMARK`

Alternatively, the integration-test `appsettings.json` can define the local SQL Server, login, and database names while keeping the secret out of the file. In that mode set only:

- `LIBDB_TEST_SQL_PASSWORD`

The committed `appsettings.json` maps the v2.3.0 verification databases to `127.0.0.1`, SQL login key `SA`, and the four local test catalogs. The password value is read from the environment at test process startup and is never printed by the test helpers. Full connection strings supplied through environment variables are accepted only for local SQL Server data sources and database names with a separated `TEST`, `LOCAL`, or `DEV` token.

Required for benchmark setup and runs:

- `LIBDB_BENCHMARK_CONNECTION`

The benchmark wrapper sets `LIBDB_BENCHMARK_ALLOW_RESET=true` only inside its process before benchmark setup or benchmark execution. Treat both setup and run as reset-capable operations against the configured benchmark database. Destructive benchmark reset is code-gated to a local SQL Server data source and the `LIBDB_BENCH_TEST` catalog.

## Primary Gate

Run dependency restore once in a normal developer shell or CI bootstrap step before the gate:

```powershell
dotnet restore .\Lib.Db.slnx
dotnet tool restore
```

Run the full orchestrator:

```powershell
pwsh -NoProfile -File .\Tools\verification\Invoke-LibDbV230Verification.ps1
```

This performs:

1. Integration test project build.
2. Benchmark project build.
3. v2.3.0 matrix DB xUnit tests.
4. Coverlet Cobertura collection.
5. ReportGenerator HTML/Text/Cobertura report generation.
6. `Assert-LibDbCoverage.ps1` coverage gate.
7. Native AOT publish gate when the AOT verification project exists.
8. BenchmarkDotNet DB setup, benchmark run, and artifact secret-pattern scan.

## Publish Workflow Gate

The `v*` tag publish workflow must not pack or push a package until the primary v2.3.0 gate has completed without skips. `.github/workflows/publish.yml` provisions a local SQL Server container from `mcr.microsoft.com/mssql/server:2022-latest`, reads the SQL login password from the `LIBDB_TEST_SQL_PASSWORD` GitHub secret, restores local tools, and runs:

```powershell
pwsh -NoProfile -File ./Tools/verification/Invoke-LibDbV230Verification.ps1 -BenchmarkJob Dry
```

The workflow then packs with the tag-derived package version and pushes only after the gate exits `0`. A missing `LIBDB_TEST_SQL_PASSWORD` or `NUGET_API_KEY` secret is a release blocker. Do not add `-AllowPartial` or any skip switch to the publish workflow.

```powershell
dotnet test .\Verification\projects\Lib.Db.IntegrationTests\Lib.Db.IntegrationTests.csproj --no-build --filter "FullyQualifiedName~Lib.Db.IntegrationTests.V230Matrix.V230TvpMatrixTests" -v:minimal
```

Run coverage collection and report generation:

```powershell

```

Run a fast benchmark smoke that still emits BenchmarkDotNet reports:

```powershell
pwsh -NoProfile -File .\Tools\benchmark\Invoke-LibDbBenchmarks.ps1 -Job Dry -Filter "*TvpBenchmarks*"
```

Run a short real benchmark:

```powershell
pwsh -NoProfile -File .\Tools\benchmark\Invoke-LibDbBenchmarks.ps1 -Job Short -Filter "*TvpBenchmarks*"
```

Run full benchmark DB setup without executing measurements:

```powershell
pwsh -NoProfile -File .\Tools\benchmark\Invoke-LibDbBenchmarks.ps1 -SkipRun -AllowPartial
```

Skip switches on `Invoke-LibDbV230Verification.ps1` and `Invoke-LibDbBenchmarks.ps1` are partial-run tooling only. Without `-AllowPartial`, a skipped gate causes a non-zero exit so CI cannot treat partial evidence as release-grade.

## Memory-Optimized TVP Opt-In

Memory-optimized TVP setup is deliberately outside the default DB setup path. It mutates durable database metadata by adding a `MEMORY_OPTIMIZED_DATA` filegroup/file container and therefore requires explicit opt-in. After the opt-in setup has been applied, `verify-libdb-bench-test.sql` treats the memory-optimized TVP objects as part of the final `LIBDB_BENCH_TEST` sync manifest.

Official basis:

- SQL Server memory-optimized table types are off by default and must be created with `MEMORY_OPTIMIZED = ON`.
- Memory-optimized table variables can be passed to stored procedures as TVPs and must have at least one index.
- SQL Server databases need a `MEMORY_OPTIMIZED_DATA` filegroup before using memory-optimized features.
- The setup turns `AUTO_CLOSE` off for `LIBDB_BENCH_TEST` before adding the filegroup because SQL Server does not support `AUTO_CLOSE` on databases that contain `MEMORY_OPTIMIZED_DATA`.

Opt-in files:

- `Verification\databases\LIBDB_BENCH_TEST\sql\run-libdb-bench-memory-optimized-tvp-optin.sql`
- `Verification\databases\LIBDB_BENCH_TEST\sql\setup-libdb-bench-memory-optimized-tvp-optin.sql`
- `Verification\databases\LIBDB_BENCH_TEST\sql\verify-libdb-bench-memory-optimized-tvp-optin.sql`

Run the authoritative opt-in smoke only against a local, disposable `LIBDB_BENCH_TEST` database after DDL/DML/EXEC approval has been granted for that database. The runner rejects non-local `-Server` values before invoking `sqlcmd`. Do not run this opt-in script against shared, staging, production, or customer SQL Server instances.

Set `SQLCMDPASSWORD` in the current shell or let `sqlcmd` prompt for the password by omitting `-P`. Do not put SQL passwords in command history, scripts, runbooks, or committed settings files.

```powershell
pwsh -NoProfile -File .\Verification\scripts\Invoke-VerificationDb.ps1 -Db Bench -MemoryOptimizedTvpOptIn -Encrypt optional -TrustServerCertificate
```

Then run the final BENCH verifier:

```powershell
pwsh -NoProfile -File .\Verification\scripts\Invoke-VerificationDb.ps1 -Db Bench -VerifyFinal -Encrypt optional -TrustServerCertificate
```

The xUnit coverage around this scenario only verifies script composition. It must not execute the memory-optimized DDL/DML/EXEC smoke. The migration-only file `Verification\databases\verify-libdb-all.migration-reference.sql` is not the default release gate and must not be treated as an authoritative orchestrator. It must not run the opt-in setup file directly. The BENCH verifier expects the final synced `21 tables / 15 TVP types / 43 SP` BENCH shape after opt-in has been applied. For a clean slate, recreate only `LIBDB_BENCH_TEST`; do not mix memory-optimized filegroup teardown into the default benchmark reset.

## AOT Warning Tracking

The Native AOT gate is a publish-and-run gate, not a coverage-percentage gate. The project `Verification\projects\Lib.Db.AotVerification\Lib.Db.AotVerification.csproj` keeps actionable Lib.Db-owned IL warnings as errors:

- `IL2026`
- `IL3050`
- `IL2060`
- `IL2070`
- `IL2072`
- `IL2067`
- `IL2065`
- `IL2090`
- `IL2091`

Provider-owned aggregate warnings are not hidden, but they are not converted to errors in this project:

- `IL2104`
- `IL3053`

Current tracking rule:

- Release gate remains valid only when publish exits `0` and the published AOT executable exits `0`.
- Any Lib.Db-owned IL warning is a release blocker.
- Provider-owned `IL2104`/`IL3053` warnings must be reviewed whenever `Microsoft.Data.SqlClient`, `System.Configuration.ConfigurationManager`, or related transitive provider packages change.
- If the provider warning set changes, update this runbook and the v2.3.0 risk ledger before release notes are cut.

## Server-Level Chaos Boundary

Server-level chaos remains outside the default gate. It requires the dedicated opt-in harness and separate setup/verify/teardown SQL:

- `Verification\projects\Lib.Db.ChaosHarness`
- `Verification\databases\LIBDB_CHAOS_TEST\server-optin\setup-libdb-chaos-server-optin.sql`
- `Verification\databases\LIBDB_CHAOS_TEST\server-optin\verify-libdb-chaos-server-optin.sql`
- `Verification\databases\LIBDB_CHAOS_TEST\server-optin\teardown-libdb-chaos-server-optin.sql`

Do not add these SQL files to the default xUnit fixture, coverage script, or benchmark script.

Run it only after explicit server-level chaos approval for `LIBDB_CHAOS_TEST`. The SQL runner rejects non-local `-Server` values, the harness requires `--enable-server-chaos`, and teardown is mandatory after any setup/run/verify sequence because the observer uses a server-level Extended Events session. The observer captures SQL text and user names in its ring buffer, so it must never be enabled on shared, staging, production, or customer SQL Server instances.

Use `LIBDB_CHAOS_CONNECTION`, or set `LIBDB_CHAOS_PASSWORD` in the current shell and let the harness build the local `127.0.0.1` SQL-login connection. Do not put the password value in command lines or committed files.

```powershell
dotnet run --project .\Verification\projects\Lib.Db.ChaosHarness -- setup --enable-server-chaos
dotnet run --project .\Verification\projects\Lib.Db.ChaosHarness -- run --enable-server-chaos
dotnet run --project .\Verification\projects\Lib.Db.ChaosHarness -- verify --enable-server-chaos
dotnet run --project .\Verification\projects\Lib.Db.ChaosHarness -- teardown --enable-server-chaos
```
